# Resource2Skill 论文解读

链接：<https://arxiv.org/abs/2606.29538>

## 一句话结论

这篇论文不是在做“更强的检索”，而是在做一件更完整的事：把教程视频、代码仓库、文章和参考素材，蒸馏成可以被软件 agent 直接调用和组合的“技能”，再把这些技能组织成一个层级化的 Skill Wiki。

它的核心价值有三点：

1. 把原本很难直接喂给 agent 的多模态人类资源，变成了可执行的技能。
2. 把技能库做成了有层级结构的 Wiki，而不是一堆平铺的文本。
3. 支持在线补技能，缺什么能力就现学现补。

## 这篇论文在解决什么问题

作者面对的是软件作者型 agent 场景，例如：

- PPT 制作
- Excel 制作
- Web 页面生成
- Blender 场景
- CAD
- UE5 场景
- Reaper 音频制作

这些任务的共同点是：真正有用的知识不是“事实”，而是“流程”和“操作套路”。

传统做法的问题是：

- 只靠文本技能库，很多视觉、时序、操作顺序信息丢了。
- 只靠 agent 自己交互轨迹，覆盖面太窄。
- 只做检索，不做结构化沉淀，技能很难复用和维护。

## 方法总览

Resource2Skill 把系统拆成四步：

1. `construction`：从资源里蒸馏技能。
2. `wiki organization`：把技能组织成层级 Wiki。
3. `selection`：先粗筛，再由语言模型挑技能。
4. `execution`：通过 MCP 接到具体软件后端执行。

它的设计点是：离线构建和在线补洞共用同一个构造器。

## 技能长什么样

论文里把一个 skill 定义成：

```text
s = (p, xtext, xvisual, xcode, m)
```

其中：

- `p`：技能在领域 taxonomy 里的路径
- `xtext`：名称、机制、适用条件、输入输出、预期效果
- `xvisual`：缩略图、截图、渲染图、示意图
- `xcode`：可执行或可改写的代码片段
- `m`：元数据和溯源信息

这比普通“文本技能卡”多了两个关键东西：

- `xvisual` 保留布局、外观、动效、空间关系
- `xcode` 保留工具调用和执行骨架

## 技能是怎么抽出来的

资源池来自四类：

- tutorial videos
- source repositories
- articles
- reference artifacts

构造器 `f_θ(r, D)` 会对单个资源做检索、抽取和规范化：

```text
tilde{s}_{1:k} = f_θ(r, D)
```

然后经过一个领域相关的接受谓词 `A_D` 过滤：

```text
Σ_D = { s = normalize(tilde{s}) : tilde{s} = f_θ(r, D), r ∈ R_D, A_D(tilde{s}) = 1 }
```

`A_D` 这 5 个检查是：

- 完整性
- 溯源可追踪
- 去重
- 多模态一致性
- 代码字段的结构可执行性

这里最重要的一点是：`f_θ` 本身不是专门训练的模型，而是“视觉能力强的 LLM + 确定性预处理 + 规则过滤”。

## 为什么视频重要

论文明确把视频看成不可替代来源。

原因很直接：

- 视频能给出时序顺序
- 视频能展示操作前后变化
- 视频能展示视觉效果
- 很多细节很难完整转写成文本

消融结果也证明了这一点：去掉视频后性能下降最明显，尤其在 Web 和 Excel 上。

## 为什么要做层级 Wiki

如果只是平铺一个技能列表，agent 需要在很大的候选空间里盲搜。

Resource2Skill 先用 taxonomy 缩小范围，再让模型读候选技能做最终选择：

```text
CK(q) = TopK_s∈Σ_D BM25(q, name(s) ⊕ tags(s) ⊕ applicability(s) ⊕ p(s))
```

然后：

```text
S(q) = π_φ(q, {Φ(s) : s ∈ CK(q)})
```

这里的意思是：

- 第一阶段：用 BM25 把候选缩到 `K=20`
- 第二阶段：语言模型从这 `20` 个里选出最终要暴露的 `n=5` 个

这比纯 BM25、纯 embedding、随机取候选都更好。

## 在线补技能是什么意思

如果离线 Wiki 覆盖不了当前需求，就沿用同一个构造器在线搜索新资源、抽技能、验证后加入临时在线池。

但要注意两点：

- 在线池不会并回离线主库
- 在线补技能只是 gap filler，不是无限扩库

论文的实验也说明：

- 在标准任务上，在线补技能几乎没额外收益
- 在新能力缺口任务上，收益很大

这说明它补的是“覆盖盲区”，不是简单加资源量。

## 实验设置

评测覆盖 7 个领域：

- Web
- Excel
- Reaper
- PPT
- Blender
- CAD
- UE5

对比了 4 个 agent backend：

- GPT-5.5
- GPT-5.4
- GPT-5.4 Mini
- GPT-5.4 Nano

主要基线包括：

- `w/o Skills`
- ClaudeCode-H
- Codex-H

## 主结果

最核心的数字是：

- 平均整体分数提升 `+11.9` 个百分点
- 在 28 个主对比 cell 里，`w Skills` 全部优于 `w/o Skills`
- 还能在 `26/28` 个 cell 上超过强 harness baseline

直观上说明：

- 不是单纯换个 harness 就够了
- 真正有效的是“技能库 + 层级选择 + 多模态表达”

## 消融结论

论文做了几组关键消融：

### 1. 只用文本技能 vs 完整 Wiki

平铺纯文本技能已经有效，但完整 Wiki 最好。

说明：

- 文本有用
- 结构和多模态更有用

### 2. 去掉视频

掉点最大，说明视频不是可有可无。

### 3. 只留部分模态

文本、视觉、代码都各自有增益，完整三模态最好。

### 4. 选择策略

层级 + LM 的策略优于：

- BM25
- dense retrieval
- BM25 + dense rerank
- 随机取全库

这说明“先用 taxonomy 定位，再让模型做语义选择”是有效的。

## 这篇论文的真正贡献

我会把它概括成一句话：

> 它把“人类教程资源”从检索对象，变成了 agent 可执行的程序性知识。

具体来说，贡献不是单点的，而是一个闭环：

- 构造器把资源转成技能
- Wiki 把技能结构化
- 选择器把技能变成可组合上下文
- 执行器把技能落到真实软件后端
- 在线补技能让系统有扩展性

## 局限

这篇也有边界：

- 依赖领域 taxonomy 设计
- 依赖资源质量和溯源
- 主要验证的是软件作者任务
- 技能抽取仍然依赖 LLM 的结构化输出能力
- 在线补技能是受控补洞，不是通用自治学习

## 我的解读

如果把这篇放在 agent 系统谱系里，它更像是在做“procedural memory”的工程化落地。

它不是让模型“更会推理”，而是让模型“记住怎样做事”。

这也是它为什么在作者型任务上有效：

- 这些任务很吃流程和格式
- 很多知识本来就适合被沉淀成可复用技能
- 多模态资源比纯文本更接近人类真实学习方式

## 关键信息速记

- 论文主题：从人类多模态资源中蒸馏可执行技能
- 核心载体：层级化 Skill Wiki
- 核心流程：construction + organization + selection + execution
- 关键提升：`+11.9` pp 平均整体分
- 关键发现：视频不可替代，层级选择优于平铺检索
